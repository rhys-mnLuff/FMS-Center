Known Simplifications

read this before treating anything above as literal firmware behavior
  • Debounce/hysteresis state machine (Safe → Watch → Flood Risk) matches the design in CALIBRATION.md for moisture_alert_logic.ino — soil-only, and per the doc "not yet wired to SMS." The shipped base_station.ino fires instantly on the first threshold-crossing reading for either sensor. This console runs the proposed debounce logic for both.
  • Reset thresholds (soil 500; water uses its own alert threshold, 200, since no water hysteresis is documented) are demo placeholders, exactly as CALIBRATION.md labels its own TRIGGER_PCT/RESET_PCT.
  • Global SMS cooldown (1 hour, shared across every node, not per-node) is modeled faithfully from Base_code's single lastSmsTime variable — watch the Events log for "suppressed" entries.
  • Water sensor direction is unverified in the real firmware (Base_code's own comment). This console uses the code's current, unverified direction.
  • "Relayed via" a specific node is illustrative. The real mesh (Sensor_code) is undirected flood-broadcast with no hop-count or path field — the base station can't actually know a packet was relayed, let alone by whom.
  • Rain Detection Node is entirely speculative — no such hardware exists in the repo yet. Sensor type, polarity, and thresholds here are placeholders modeled after the existing soil sensor for planning purposes only.
  • Cellular signal and cloud-upload failures are simulated — the base station's SIM7600/A7670 does support the real AT+CSQ command this models, but the firmware doesn't currently read or log it. Upload failures shown here are invented to illustrate what "silent data loss" would look like given base_station.ino never checks its own HTTP response.
  • The Calibration Wizard generates simulated bench readings, not data pulled from any field node — matching how the real protocol works (a soil sample on a bench, per CALIBRATION.md), but "Complete calibration" here writes to this session's in-memory state only. It does not persist to CALIBRATION_DATA.md or affect the farmer-facing page, which runs its own independent simulation.
  • Battery health has no real sensor today. Neither Base_code nor Sensor_code ever reads a voltage divider, and HARDWARE.md notes panel wattage/battery capacity aren't finalized yet. The battery %, the day/night charge cycle, and the brownout-causes-offline behavior here are fully simulated — modeled to plan what a future firmware battery check might look like, and to mirror the real brownout symptoms HARDWARE.md's bring-up notes already describe ("Resets or LED dies during send" → power brownout).
  • "Offline" detection is dashboard-side inference (time since last packet exceeds a threshold), not a heartbeat the firmware sends — realistic, since it's exactly how the eventual cloud dashboard would derive it from upload timestamps, but the specific threshold/logic is this demo's own design, not documented anywhere in the repo.
  • The "Run Fleet Diagnostic" report is generated client-side from current simulated readings — it's a UI feature of this console, not a firmware or cloud capability that exists today.
  • RX/cloud console lines match the real packet format and query string exactly, but base_station.ino doesn't currently print received packets to Serial — only sensor_node.ino prints "Transmitted:"/"Bounced:" lines.
